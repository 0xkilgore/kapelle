# Native website publication

This is an isolated implementation candidate. No production facts adapter, effect policy, credential, Dispatch enqueue bridge or Vercel mutation is installed by importing it. `openFrameworkRuntime` defaults to closed effects. The owner HTTP endpoint rejects execution commands even when an in-process effect policy is configured.

`publicationManifest` validates exact immutable inputs. `publicationArtifact` freezes canonical bytes/identity; `publicationProposal` creates a ReviewIntent v2 `WEBSITE_PUBLICATION` / `publish` proposal with expiry. Identity includes Report bytes/source, Git commit/tree/files/lockfile, production build receipt/output/recipe/site evidence, optional staged deployment ID with trusted staging receipt reference/hash, owner/scope, Task mapping/commitment hash, and target project/team/domains/alias-deployments. The Vercel adapter requires both staged bindings and manifest contract `kapelle/website-publication/v2`, which adds complete alias inventories and explicit direct/redirect domain roles, destination, configured/effective status and path/query preservation. V1/v2 parsing and hashes remain unchanged; the new executor rejects v1 and never patches an accepted proposal. Report read/feedback revision and observation timestamps are excluded. A changed input requires a new manifest/review; there is no mutable approval JSON ledger.

`PublicationFactsAdapter` reads trusted Report, source, build, target and Task ports and verifies exact bytes and identities. `gitSourceReader` uses a fixed server repo map and argument-based read-only Git calls. `vercelTargetReader` uses fixed-origin, bounded, credentialed GETs for project, aliases and deployments, then repeats the snapshot. Unsupported routing, ownership mismatch, missing proof and drift fail closed. This reader is **not provider mutation fencing**. Vercel project/alias/deployment read APIs do not establish compare-and-swap for a future promotion.

`publicationReviewPlan` returns native allocation and CREATE_REVIEW commands. Version 2 is explicit; default framework allocations remain v1. The service reads the initial model version and global operations in one scoped transaction. It rejects imported initial state and in-place model upgrades until full spine replay is qualified. The versioned allocation adapter preserves the reserved native genesis version; the qualified Reactor's existing Drive convenience method hardcodes version 1. Existing v1 reducers and approval hashes remain unchanged. The generated archive upgrade retains historical bytes and adds null expiry.

`websiteEffectPolicy` admits only the exact manifest/instance's native website review. `publicationEffectFacts` adds independently verified Dispatch and delivery facts. Loss of old-target admission facts after a successful promotion does not block recording a verified outcome. `PublicationCoordinator` requires an approved exact proposal, consumes one native reservation, rechecks current capabilities/expiry/source/target before invocation, and reconciles the same operation after uncertainty. Delivery requires matching provider/source/build evidence, current aliases, exact live-site bytes, and a stable second alias read. No method marks the parent Task complete.

The invocation claim is native ReviewIntent v2 `CLAIM_EXECUTION`, with one permanent operation/attempt/executor binding. Only the process that newly confirms the claim receives an ephemeral invocation right; a prior claim or ambiguous acknowledgement never grants another. Synthetic SQLite Dispatch storage exists only to exercise enqueue idempotency in tests. A retryable projection outbox lease is not an execution claim: `delivered_at` there means an envelope was appended, not that a website was published.

Native `kapelle/dispatch` v1 now retains the immutable request and verified lineage. A delegated publication binds `originDispatch` in its manifest; `websiteEffectPolicy` reads that actual scoped native document and every ancestor/agent at reservation, claim and final admission. It requires the accepted input hash, intended executor, original Task commitment and independently current grants. A caller-supplied list of native parents cannot satisfy this proof. Recording a verified outcome remains possible after revocation or cancellation; those changes cannot erase a real external effect. See `../dispatch/README.md` for the model/transport boundary.

## Transport and provider candidate

The separate `./publication/adapters` export supplies the existing Manager queue/outbox bridge, bounded machine HTTP clients/handlers, explicit executor composition, scoped Task Authority reader, and Vercel staged-production adapter. These are implemented and tested against the actual Manager reactor/migrations, native Reactor/journal and fake provider transport. They are not installed. See [ADAPTERS.md](ADAPTERS.md) for contracts, host wiring and recovery.

The Vercel adapter durably holds the project before native reservation/claim and serializes the entire write/reconciliation sequence across executor instances sharing the journal. It records contact before a single POST. Verified native delivery records an observation; it never releases the project hold or proves the original provider request has settled. Trusted upload evidence binds the exact uploaded file inventory to the build and returned deployment; intended staged routes/assets are read and hashed before promotion. Native facts require that receipt before approval. Read-only provider preflight runs before the permanent invocation claim and again before contact. It verifies project policy, complete project/deployment/generated-alias inventories, direct/redirect roles, current target, external writer fence and native admission. Configured rolling releases are rejected; delivery requires the documented PROMOTED state, preserved aliases/routing, direct-domain bytes and exact redirect evidence. Redirects may point only to a bound direct domain; loops/chains and incomplete inventories fail closed. A saved contact can only be reconciled. Vercel promotion has no documented compare-and-swap token; the host must supply a real project-wide writer fence. Local SQLite serialization and the per-deployment `--skip-domain` staging override alone are insufficient.

## Remaining production bindings

- Install the real Task/Report/source/build readers and explicit Manager-to-native Task/owner mapping for future work.
- Preserve immutable Vercel-ready build output, BuildReceipt and site hashes, then use a qualified staging producer to retain the actual upload inventory and returned deployment identity in a trusted staging receipt. Bind that receipt into a new exact proposal. The supplied reader is not a staging producer; a successful local Next build alone is insufficient.
- Qualify the scoped REST credential, full domain/alias/deployment evidence, project policy and exclusive writer fence. The connected app returned 403, while existing CLI project/production inspection succeeded; access is not universally blocked.
- Mount Manager/executor routes and a bounded dedicated delivery/reconciliation wakeup using three distinct Manager, executor and owner-decision credentials. Wire actual native approval admission, facts and effect policy. Generic Manager scheduler claiming is intentionally excluded from these held queue entries.
- Bind retained native agent/Dispatch lineage, grants, owner/scope/instance and proposal expiry. Product owns owner-session/CSRF and its decision-only facade; machine credentials cannot issue decisions.
- Integrate native delivery projection into the linked Report/Task views. Task completion remains an independent validated Task Authority operation.

No live review, approval, grant, dispatch, staged deployment or publication is created by this candidate. Recovery and code rollback must preserve native reservations/claims, project holds, active-run history, provider contact metadata and Manager operation keys. Holds now support permanent, request-bound settlement tombstones after native terminal evidence, and a sealed no-contact recovery path. The runnable isolated host qualifies these against a synthetic transactional target. Real Vercel contact still has no installed settlement oracle; observed delivery alone leaves its hold occupied.

A read-only qualification against a real site project found Git-triggered deployments enabled, an owner manual/API writer, and an apex redirect. V2 now represents and tests that redirect topology, including generated aliases, without changing production. The full real project/deployment alias inventory has not been qualified against this bounded reader: all project aliases must belong to one current production deployment, with at most ten domains; unrelated preview/branch/manual aliases and other unsupported routing are rejected. The strict all-writer guarantee remains unenforceable with the documented controls in the observed configuration. Preserve existing routing and keep publication blocked pending writer assurance, real staging and installed composition. Known preflight failures do not consume an invocation. A trusted host can now seal and reconcile a consumed claim with provably no provider contact; any saved contact still needs independent terminal request proof before release. No browser/owner command can force either outcome.


## Proposed writer policy (disabled)

`proposedWriterPolicy` builds an immutable, content-addressed `kapelle/website-writer-policy/v1` artifact. Its explicit `brokered-automation-owner-override` mode covers all managed automated production writes through one broker, while acknowledging that the Owner can still write manually. It binds project/team/broker/generation, proposed Git disconnection and credential isolation, pre-claim durable holds, no ambiguous retries or timeout release, observed-result semantics and drift pause. These are proposed requirements, not claims about an installation.

A new `kapelle/website-publication/v3` manifest embeds that artifact and verifies its content hash and target. Any policy change creates a different approval and Dispatch identity. The only supported policy status is `PROPOSED`; coordinator and native effect policy deny reservation/claim, and the Vercel adapter remains strictly v2-only. Existing strict `assertExclusiveProjectWriter` requirements are unchanged. No Git setting, credential, deployment, profile or production effect gate is changed. Activation requires a separately reviewed implementation and a new exact proposal, not relabeling an old approval.

## Runnable isolated host

`openPublicationHost` composes the existing native decision facade, actual Manager queue/outbox, scoped executor HTTP, explicitly bound facts and read-only `/publication-status`. It retains host/review/manifest/Manager identity in the native journal, enforces distinct owner/Manager/executor credentials at runtime, and offers one bounded wakeup after an accepted decision and at startup when explicitly enabled. It does not provision live grants or install a scheduler.

See [HOST.md](HOST.md) for the executable synthetic demo, retained state, settlement proof boundary, no-contact recovery and production dependencies. The demo uses new synthetic Task/Report commitments and real native ReviewIntent/Dispatch documents; it never reuses the completed cleanup Task.
