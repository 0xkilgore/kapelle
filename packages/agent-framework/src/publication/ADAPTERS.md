# Publication transport and executor adapters

Isolated candidate, exported at `@kapelle/agent-framework-models/publication/adapters`. Importing it starts no listener, scheduler or provider request. `publicationExecutorAdapters` requires an existing authority and explicit configuration; constructing the provider adds project-hold, active-run and contact metadata tables to that authority's existing command journal. It does not create another Task, native Dispatch, approval or execution authority.

## Authority and stable identity

Native `kapelle/dispatch` owns requester, exact input, lineage, grants and result. Native ReviewIntent v2 owns the decision, effect reservation, permanent invocation claim and delivery evidence. The existing Manager queue/outbox carries the same intent and references; it is a transport projection.

`ManagerPublicationStore` accepts the existing `SqliteDispatchReactor` and `DbAdapter` interfaces, pinned team/owner/scope/review/instance/executor and manifest. New enqueue requires its configured native admission callback. Existing saved binding reads permit recovery without granting another invocation. The permanent operation key and payload uniqueness come from the existing Manager queue. The adapter verifies its real transactional outbox; an outbox-disabled installation is rejected without changing that setting.

- Queue key: `publication:<ownerId>:<intent.key>`.
- Native effect operation: `publication-operation:<SHA256 of canonical intent>`.
- Dispatch reference: the actual queue `dispatch_phid`.
- Outbox reference: the actual `dispatch.requested` operation ID, checked within the pinned team and causation.
- Envelope: `kapelle/publication-transport/v1`, including exact intent and optional originating native Dispatch reference/hash.

Queue entries use `kapelle-publication`, `runtime=other`, `provider=local`, `promote=false`, and a held `not_before_at` in year 9999. A dedicated host wakeup calls `store.deliver(executorClient)`; generic scheduler claiming cannot run these entries. After ambiguous acknowledgement, retain the same binding and use `store.deliver(executorClient, "reconcile")`. Repeating `run` cannot create another native invocation claim either. This is not the Manager's LLM or build-promotion channel.

## Private route contract

Each installed route handles one exact review/manifest/instance binding. Credentials are server configuration, never request fields. Origins must be HTTPS or numeric loopback HTTP; redirects are denied. Responses and request bodies are bounded; transports have deadlines and never automatically retry a POST.

| Listener | Method/path | Exact input | Result |
| --- | --- | --- | --- |
| Manager | GET `/binding` | none | Saved Dispatch binding, or 404 |
| Manager | POST `/ensure` | `{intent}` | Same saved binding after native admission and atomic queue/outbox insertion |
| Executor | POST `/run` | `{operationId,dispatchRef,outboxRef}` | Native delivery receipt after one claimed invocation or reconciliation |
| Executor | POST `/reconcile` | same exact saved identifiers | Native delivery receipt from read-only provider reconciliation |

The executor response is `{reviewId,operationId,dispatchRef,status,evidenceId,occurredAt}`. Status is `DELIVERED`, `FAILED` or `UNCERTAIN`; timestamp and evidence ID come from native delivery. The client verifies exact operation/review/Dispatch identity. Manager saves this typed receipt in `result_json`, projects definitive status/completion time and advances its update time monotonically. Cancelled queue status is retained. A delayed UNCERTAIN response cannot replace an existing terminal projection. These fields do not complete a native Task. Manager `done` means a retained native delivery result, not a free project lane, settled provider request or continuously current website. The response contract remains unchanged; project hold state is separately available to the trusted host through `provider.holdStatus(binding)`. The composed owner facade exposes it through authenticated read-only `/publication-status`, separately from the native delivery result.

The machine surface denies browser Origin and owner-session headers, caller actors, arbitrary commands/targets/manifests and decision routes. Constant-time Bearer comparison checks the dedicated credential. `publicationExecutorAdapters` requires distinct Manager, executor and owner-decision credentials at construction and again at every executor request; a rotation collision fails closed with 503. Authentication failures return 403; unadmitted or unconfirmed routes return sanitized 409. No response includes provider credentials.

## Host wiring

1. Load the retained manifest and native review/instance/agent/Dispatch references; construct the existing native authority with trusted source/facts ports and an explicitly scoped effect policy. Default production effects remain closed.
2. On the Manager host, construct `ManagerPublicationStore` with its actual queue and database. Bind `admit` to actual native exact-owner-approval readback, such as `approvedPublication` when the scoped authority is available in-process. A separate-host installation must provide the equivalent authenticated native read; caller booleans are not admission. Mount `managerPublicationHandler` on the private machine listener.
3. On the executor host, call `publicationExecutorAdapters(authority, config)`. Wire its `dispatch` and `provider` into `publicationEffectFacts`, and its `effectPolicy` into the authority before exposing its handler. Supply a stable, unique `brokerHostId` for the trusted executor installation and the single durable journal used by every executor for this project. The factory binds provider admission to `authority.effectAdmission` and delivery observation to actual native terminal readback. No native receipt releases the project hold. Mount only this handler with the executor token.
4. Configure a dedicated bounded Manager delivery/reconciliation wakeup and `PublicationExecutorClient`. Keep Product's decision-only owner facade separate. Existing host authentication and deployment configuration are not installed by these library constructors.
5. Bind `PublicationTaskReader` to the fixed Task Authority origin/token, native Task ID, Report sourceRef, project and native/framework owner mapping. Its commitment hashes title/body/native owner; unrelated revisions do not alter that commitment. DONE/ARCHIVED or changed content blocks new publication admission. The Manager Task reference is explicitly supplied, never inferred from a slug.

## Vercel provider

`VercelPublicationProvider` uses fixed-origin REST reads and one `POST /v10/projects/{projectId}/promote/{deploymentId}?teamId=...`. It requires a new `kapelle/website-publication/v2` manifest with explicit routing, plus a READY, unused STAGED production deployment with `aliasAssigned=false`. The project must belong to the bound team, have `autoAssignCustomDomains=true`, and have absent/null `rollingRelease`; any configured rolling release is unsupported.

The v2 target retains exact alias IDs/deployment IDs and adds `routing` (`kapelle/vercel-routing/v1`): complete `projectDomains`, `deploymentAliases`, `productionAliases`, and one direct/redirect route for every bound domain. A redirect binds its destination, nullable API `configuredStatus`, effective HTTP `status` (301/302/307/308), and `preserve-path-and-query` policy. Its destination must be a bound direct domain. Chains, loops, external destinations and URL/path destinations are rejected. A null API override is not assumed to mean a particular status: a credential-free public HEAD observes and verifies the effective value.

The reader reconciles the complete project-domains list, project-scoped alias list, current production deployment's alias list, project/deployment advertised production aliases and per-alias detail. It reads the entire snapshot twice. Both paginated endpoints must return an explicit null next cursor at limit 100; incomplete responses are rejected. The manifest bound is ten total aliases. Every project alias must belong to the same current READY/PROMOTED production deployment, and the union of project domains and deployment aliases must exactly cover them. Non-project aliases must be direct `.vercel.app` aliases. Projects with unrelated preview/branch/manual aliases, mixed deployments, custom environments, microfrontends or larger inventories are intentionally unsupported; they are not silently filtered out. See the official [project alias inventory](https://vercel.com/docs/rest-api/aliases/list-aliases) and [deployment alias inventory](https://vercel.com/docs/rest-api/aliases/list-deployment-aliases). These inventories establish the approved scope; they are not an atomic provider promotion plan or writer fence.

V1 and v2 manifest parsing, artifact bytes and proposal hashes are preserved. The new Vercel executor rejects v1 construction and never upgrades an accepted proposal in place. Any outstanding v1 contact must retain its pinned prior receipt-only implementation and journal; do not migrate an active lane by patching its manifest. V2 requires a new artifact/review and owner decision. The artifact's content version remains 1 because every immutable content-addressed artifact is first created at version 1; the manifest contract carries the new schema version.

Every staged manifest binds `build.staging={receiptRef,receiptHash}`. The trusted staging runner must retain an immutable `kapelle/vercel-staging/v1` receipt linking the BuildReceipt reference/hash, canonical uploaded file inventory/output hash, recipe, production environment, source commit/tree/lockfile, team/project, returned deployment ID and unique deployment host. `outputHash` is the digest of the path-sorted uploaded `{path,hash,bytes}` inventory, including the provider-compatible build output. The receipt must describe the files actually uploaded; a local build or caller-supplied deployment metadata is insufficient. `stagingReceiptReader` reads a fixed server-configured reference-to-file map; it neither uploads nor creates trustworthy producer evidence. Production staging and its retained evidence remain a separate installation prerequisite.

Native facts validate this receipt before approval/admission. Provider preflight validates it again and checks the returned deployment host, policy, complete routing/alias inventory, writer fence, intended staged route/asset bytes, redirect evidence and repeated old-target snapshot before the permanent invocation claim. Deployment metadata (`kapelleCommit`, `kapelleTree`, `kapelleBuildHash`, `kapelleBuildReceiptHash`) is an additional cross-check only. The provider repeats preflight, the writer check and current native effect admission before contact. An optional separate `stagedProtectionBypass` credential is sent only to the receipt-bound unique staged host; it must differ from the REST token. Byte reads deny redirects. Redirect HEAD reads use manual handling and never follow Location. Public reads carry neither credential.

Before native reservation/claim, `withOperation` commits an exact operation/binding/deployment hold, unique per team/project, into the existing native command journal. A separate active-run record serializes all asynchronous reserve/claim/write/reconciliation work; overlapping requests fail busy, including requests through another provider object or SQLite connection. Provider mutation and delivery acknowledgement require the active invocation context. Short SQLite transactions never span asynchronous work. The provider additionally persists contact before sending, with permanent deployment uniqueness. A restart or any HTTP outcome never clears the claim or authorizes a second POST. Even definite HTTP rejection is conservatively reconciled as unknown unless actual delivery evidence establishes an outcome.

Provider lookup requires the documented `readySubstate="PROMOTED"` and `aliasAssigned=true`, the exact deployment, complete unchanged routing/alias identities, bounded raw bytes on each direct domain and a stable second target read. Redirect verification checks root, every site-proof path, and each path with a fixed query probe; status and absolute HTTPS Location must match the approved destination and preserve path/query exactly. The native delivery boundary independently repeats direct-byte/redirect checks and includes their proofs plus the full target in evidence identity. It does not require `promotedAt`; ROLLING is not a completed promotion. Unknown/missing/mismatched evidence stays UNKNOWN; this adapter does not fabricate a terminal failure. `confirmDelivery` runs inside the guarded coordinator after native commit and stores only an evidence reference. The contact remains `settled=0`, and the durable project hold stays occupied. An Owner may independently promote the same candidate while this broker's request is delayed; matching aliases and bytes cannot distinguish those cases. A transport response, timeout, age, owner acknowledgement or process exit does not release the hold. There is no caller-controlled release API. The separately qualified settlement port and local no-contact seal described in [HOST.md](HOST.md) are trusted-host recovery paths, never owner/browser commands.

Vercel documents that staged production promotion can preserve the existing build, while promoting a preview can rebuild. The adapter therefore does not deploy, build, promote previews or retry a previously promoted deployment. See [promotion behavior](https://vercel.com/docs/deployments/promoting-a-deployment) and [REST promotion endpoint](https://vercel.com/docs/rest-api/projects/point-production-traffic-to-a-given-deployment).

The CLI's [`--prod --skip-domain`](https://vercel.com/docs/cli/deploy#skip-domain) stages with a per-deployment `autoAssignCustomDomains=false` override. This is compatible with the project's `autoAssignCustomDomains=true` requirement; it does not change project policy or exclude competing writers. Creating that staged deployment is an external mutation, not performed by this library or its qualification tests.

There is no documented conditional target/CAS token on the promotion endpoint. `assertExclusiveProjectWriter` must be backed by a real installation constraint covering Git promotion, manual/API writers and other hosts for the entire operation. A no-op callback is suitable only for the fake-provider fixture. The local SQLite lane and read-twice snapshots alone cannot establish this constraint. Do not install this provider until it is proven.

## Qualification and recovery limits

Tests load the inspected Manager reactor and migrations from `KAPELLE_PUBLICATION_MANAGER_ROOT` and explicitly import its installed `dist/db/sqlite-adapter.js` (better-sqlite3), using temporary isolated storage. There is no substitute-driver fallback. The runtime must match that native module ABI. This qualifies the installed database adapter against the source reactor/migrations, not a whole installed-dist Manager process or live database. Native tests use actual scoped Reactor/PGlite and the retained command journal. Provider responses, writer fence, build/site and most facts are synthetic; no Vercel mutation is performed.

The complete native → Manager HTTP → executor HTTP → provider chain covers lost executor acknowledgement, unknown provider contact, acceptance with lost provider response, restart, same-operation reconciliation and native-backed Manager projection. Additional cases exercise credential separation/rotation collision, forged identity, queue/outbox drift, target/build/domain/policy/fence changes, one contact, immutable approval identity and hold persistence. New cases prove pre-claim hold ordering, restart before claim/after claim/lost native claim acknowledgement, concurrent run/reconcile while POST is pending, same-candidate Owner observation, and retention after native DELIVERED and later drift. A separate actual child-process SIGKILL test qualifies active-run retirement and durable hold retention. Provider transport is synthetic; a full executor process kill against real Vercel is not qualified.

Known preflight rejection leaves the existing reservation but no invocation claim or contact; correcting the missing facts allows the same operation to proceed. Preflight is repeated after claiming, so a race, crash, rejected request or ambiguous contact can still leave a consumed claim unresolved. No operator/native terminal-resolution path is implemented here. An unknown contact stays unresolved without a second promotion. Preserve all native records, Manager operation keys, project holds, active-run history, observations and contact rows across restart and rollback. Never copy/restore an active journal into a second running installation. An older executor does not enforce these holds and is not a safe execution rollback. A provider rollback is a separate reviewed effect, not clearing a claim or replaying the original approval. If installation facts or credentials are unavailable, stop new effects and retain receipt-only reconciliation capability.


## Host recovery and adoption boundary

The installation marker binds the hold schema to the supplied host identity. A restarted executor may retire an ACTIVE run only when `process.kill(pid, 0)` on that same host proves `ESRCH` (the process no longer exists). Live or reused PIDs, permission errors and different host identities remain blocked. Retiring a run preserves the hold, native claim, contact and history; it only allows the same operation to reconcile. No timeout, PID age, manual acknowledgement or caller takeover flag is accepted. A host restart may conservatively leave a reused PID blocked. Cross-host failover, copied snapshots, authority/journal loss and recovery after PID namespace changes require separate qualification. Install one canonical durable journal per project; this local guard cannot coordinate independent journals or other provider writers.

Automatic adoption refuses any pre-marker journal containing a provider contact, including old `settled=1` rows, or a prepared/retained `CLAIM_EXECUTION`. Those records may hide unresolved pre-contact claims or delayed requests. Preserve pinned v1/v2 receipt readers and the original records for recovery; do not resume execution through the old release-on-delivery behavior. Migration of active/previously contacted lanes requires separate evidence and review. Historical manifest compatibility does not mean active-journal migration is safe.

The isolated host qualifies an immutable per-request settlement oracle using an atomic synthetic target, and a permanent no-contact seal before native failure reconciliation. No such oracle is installed for real Vercel. Its successful observed publication still leaves subsequent operations blocked unless the exact original request is independently proved terminal; generic latest-promotion status is insufficient. Recovery availability remains a production installation gate. No production writer mode is activated; see [README.md](README.md) for the disabled v3 proposed policy artifact.


### Reproducible adapter and recovery qualification

Run `scripts/qualify-publication-adapters.sh` from this package (or its repository root). It requires explicit `KAPELLE_PUBLICATION_MANAGER_ROOT`, `KAPELLE_SCOPED_REACTOR_ROOT`, `KAPELLE_PLATFORM_MODELS_ROOT`, `KAPELLE_WORKER_HOST_TSX` and `KAPELLE_QUALIFICATION_NODE`; missing prerequisites fail before tests rather than silently skipping qualification. Use a Node supporting node:sqlite and compatible with installed better-sqlite3; the September22 packet used Node23.7.0. Dependencies must already be provisioned. Synthetic loopback listeners may require sandbox network permission.

The integrated fixture retains installed adapter SHA256, Node version and ABI. The queue proof starts three separate Node processes: enqueue, project a synthetic native terminal receipt, reopen/read without contacting the executor. It checks one stable queue identity, one requested/completed outbox pair, stable terminal receipt and identical adapter identity. Other tests retain the competing-enqueue, lost acknowledgment and non-generic claimability cases.

Full native-host cases exercise a settlement reader that is unavailable, supplies a wrong binding, or loses acknowledgment after durable settlement. Native delivery remains distinct from UNPROVEN request settlement; restart retains the exact operation/dispatch/outbox and performs no second provider POST or native invocation. After valid terminal proof, one tombstone remains. The private Task reader is also tested over real loopback HTTP: completing a Task, changing its commitment or linking a different output refuses subsequent admission without writes.

All provider target changes and terminal proofs in these tests are synthetic. They do not supply the real provider's immutable request-terminal contract, an exclusive-writer installation constraint, Task completion, or a production deployment claim. Keep the existing live effect gates until those installation-specific facts are proven.
